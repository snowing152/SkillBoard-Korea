# 0014. REST + OpenAPI generated from Zod via nestjs-zod; typed client for web and mobile

Date: 2026-10-14 · Status: Accepted

## Context
Web and mobile need a typed client. The contract must come from the shared Zod schemas, not be redeclared
as Nest DTO classes with decorators (which agents would then let drift).

## Decision
- REST, JSON, versioned by path prefix `/v1`. Resource-oriented routes: `GET /v1/talents/:slug`,
  `PATCH /v1/me/talent-profile`, `POST /v1/reports`.
- `nestjs-zod`: DTO classes are one-liners `export class CreateXDto extends createZodDto(CreateXSchema) {}`
  that wrap the shared schema. Global `ZodValidationPipe` validates bodies/queries; `@ZodResponse` or
  `ZodSerializerInterceptor` validates outputs. Invalid output is a 500 in dev, so drift is caught.
- OpenAPI: `@nestjs/swagger` + `cleanupOpenApiDoc()` from nestjs-zod. Served at `/docs` (dev only) and
  written to `apps/api/openapi.json` by `pnpm --filter api openapi:generate`.
- Client: `packages/api-client` = `openapi-typescript` (types) + `openapi-fetch` (runtime, plain `fetch`,
  works in Next.js server/client and React Native). Regenerated by `pnpm api-client:generate`; CI fails if the
  committed file is stale.

## Consequences
Three artifacts stay in sync by construction: Zod schema → runtime validation → OpenAPI → client types.
Agents must never hand-write types for API responses. Nest's `class-validator` is not installed, to remove
the temptation.
